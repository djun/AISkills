# 文档与汇报

用户要求把已有事实、进展、变更、决定或项目知识整理成面向特定受众的产物，或实施会使权威文档失真时读取。新方案、设计或审查仍由对应能力负责；名称、模板和载体服从任务。内容动作不自行扩大为外部提交、发送或系统操作，用户指令、上下文或既有约定已明确对象与动作时继续完成。

## 先定交付与授权

先分清用户要直接返回文案、修改项目文档，还是填报 / 发布到指定系统。外部对象与动作未明确时默认交付可审阅正文；页面、工具、待办或表单的存在不等于写入授权。已明确时按 `references/dao/authority.md` 核对账号、可见范围、字段与确认边界后完成。

只写证据支持的字段；完成度、工时、负责人、日期、状态和承诺不得从任务数、提交数或语气推断。缺值只阻断保存、发送或个别字段时，仍按既有格式交付其余完整正文并保留待补位，再只问阻断后续动作的最小问题；只有正文自身无法成立时才先问。

## 取证与裁剪

证据依次取自：用户描述与指定材料 → 目标文档、模板和项目规则 → 指定范围内的 git 记录与相关 diff → 相关文件和当前对话。只读足以支撑内容的最小范围，不灌入大 diff、全仓盘点或无关历史。

没有可核实内容时直说；可以给带明确占位符的骨架，但不能用通用套话冒充真实进展。语言、格式和语气服从用户要求、受众与项目惯例。

## 日报、更新与变更文案

- 既有格式或模板的结构就是交付契约：沿用标题、日期、分区、必填字段与信息粒度，逐栏替换本期事实；缺值留空或标为待补，不改成普通摘要，也不靠删除标题、日期或字段化解缺口。没有既有格式时，让多个独立事项保持可扫读，优先写可核实的“动作 + 结果”及影响结论的验证。
- 完成项、问题 / 风险、待办与下一动作分开。下一动作以已确认安排为主；逾期但无完成证据时保留原责任与日期，标为待确认或逾期，并给出确认、重排或补负责人 / 日期的当前动作。建议单列为候选，不冒充承诺。
- 干系人更新区分事实、提案、风险、决定和下一动作；讨论中事项不写成承诺。
- commit message 凝练当前变更；PR 文案按需补背景、主要改动、验证、风险和真实未决项。没有运行的验证不写成已通过。

## 项目指南

先读现有 README、规则文件、关键配置、目录和相关文档，再选择唯一主文档。优先更新已有 README、PROJECT 或 docs 入口；没有合适 owner 且用户确实要求落盘时才新建，不复制平行指南。

区分用户确认、代码可见、已验证和仍待确认的内容；文档与代码冲突时标明来源和影响，不任意选择一方。按受众裁剪项目目标、结构、关键命令、高风险区域、术语、协作方式和验证入口；高频歧义才进词汇表，高代价且需长期追溯的架构决定才建议 ADR。

实施使公开接口、配置、命令、操作方式、已确认决定或维护知识过时时，更新直接 owner；现有内容仍准确或内部细节已由代码与测试承载时，不新增文档。

## 验成

正文以可直接审阅或发送为完成；已有格式或字段契约时，交付前按原结构逐项勾销，标题、日期、分区、必填值或必要占位不得缺失，也不得用摘要替代。文件任务以目标 diff 和必要检查为证据；外部填报 / 发布以系统真实响应和终态为证据。只生成正文时，不声称已填报、已发送或功能完成。
