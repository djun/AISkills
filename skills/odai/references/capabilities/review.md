# 审查

用户要求审查代码、diff、目录、仓库、UI 或设计系统时读取。默认只读并先报告问题；用户同时授权修复时，先固定已确认的问题，再进入实施。

## 记录问题

审查范围按以下顺序确定：用户明确指定的范围 → 与变更实际相关的文件和引用 → 当前 diff。先理解变更目的、项目规则和真实调用关系；证据不足时不判为缺陷。

每个问题都要给出紧凑定位、问题本身、触发条件或原因、实际影响、最小修复方向和针对该问题的复查方式。用户说“先别改”只限制写入，不省略建议。严重度按对当前目标的真实影响判断：

- **阻塞**：会造成正确性、安全、数据、关键体验或发布风险，当前目标不能据此通过。
- **非阻塞**：不阻断当前目标，但存在明确的维护、性能、清晰度、一致性或后续风险。
- 没有问题就明确说明在当前范围内未发现问题，不凑数；证据不足的观察单列为未覆盖或待确认。

## 检查范围

只选择与当前变更有关的方面，不把清单变成仪式：

- 意图、命名、责任位置和实际行为是否一致。
- 数据、计算、I/O、资源、性能和生命周期是否正确。
- 格式、状态、兼容、可访问性与用户操作是否完整。
- 输入、注入、权限、敏感信息和外部副作用是否安全。
- 异常、边界、依赖失败、恢复与退路是否成立。
- 职责、耦合、复用和扩展成本是否与当前改动相称。

结论将决定合并或发布、要求连续多轮无阻塞问题、全仓 / 安全审查或长修复过程时，读 `references/techniques/review-modes.md`。UI 与交互按 `references/capabilities/design.md` 和相应领域资料复核。审查 agent 始终只读；采纳和修复协作按 `references/dao/leverage.md`。

结论先给问题，再给总体判断、未覆盖范围和剩余风险。建议数量不能代替风险判断。
